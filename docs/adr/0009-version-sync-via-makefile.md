# ADR-0009: Three version manifests synchronized via Makefile

- **Status:** Accepted
- **Date:** 2026-04-01
- **Deciders:** Mikołaj
- **Tags:** release, versioning

## Context

Tauri apps carry three independent version strings:

- `package.json` — npm metadata.
- `src-tauri/tauri.conf.json` — embedded in the bundle.
- `src-tauri/Cargo.toml` — Rust crate version.

They must agree at release time, otherwise installer metadata mismatches binary metadata.

## Decision drivers

- No upstream tool keeps these three in lockstep.
- Manual editing is error-prone — easy to bump two of three.
- Don't add a version-management dependency for a solo project.

## Considered options

1. Single version in one file, build steps inject into the others.
2. Adopt a third-party tool (changesets, release-please, cargo-edit).
3. `make release` target with `sed -i` over the three files; deterministic and visible.

## Decision outcome

Chosen: **Makefile-driven sync**. `make release` bumps all three files atomically, runs `git-cliff` to update `CHANGELOG.md`, commits, tags, and dual-pushes (see ADR-0008). `make rerelease` re-tags the current version and force-pushes.

### Positive consequences

- One command, single commit, no tooling to install.
- `git diff` on the release commit makes the bump auditable.

### Negative consequences

- Three files to grep when changing the version string for any reason.
- `sed` is fragile to formatting changes — if any file's version line changes shape, the Makefile must follow.

### Follow-up

- Do not edit `CHANGELOG.md` by hand — it's regenerated by `git-cliff` (config in `cliff.toml`).
